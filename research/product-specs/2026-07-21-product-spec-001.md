## Executive Summary

Explainable Delivery Ops

## Pros & Benefits

- Converts fragmented, low-volume deliverability evidence into a repeatable incident workflow instead of an opaque score.
- Separates accepted, inboxed, junked, suppressed, forwarded, and unknown states; prevents damaging “all green” conclusions.
- Rule-first design is auditable, cheap, and useful before paid seed-list or provider integrations.
- Shared case history, redacted support packets, and scheduled rechecks create retention for agencies/MSPs managing many domains.

## Cons & Risks

- Provider reputation is intentionally opaque; the product must show hypotheses and confidence, never promise inbox placement.
- Manual evidence is incomplete and can be misleading; every conclusion needs provenance, freshness, and an explicit missing-evidence action.
- Header uploads and provider exports contain sensitive data; redact on ingest, encrypt at rest, use short-lived object URLs, and enforce tenant isolation/RBAC.
- Forwarding, delegated “Send As,” shared pools, and recipient-specific rules can create contradictory observations; model per-hop and per-recipient scope rather than flattening them.

## Proposed Tech Stack & Tools

- Frontend: **Next.js + TypeScript + Tailwind CSS** — one maintainable full-stack codebase, fast CRUD/UI delivery, server-rendered authenticated workspace.
- API/domain layer: **Next.js Route Handlers + Zod + Prisma** — typed validation and a small, testable rules service without a separate microservice estate.
- Database: **PostgreSQL (Neon or Supabase)** — durable multi-tenant incident/evidence model, JSONB for raw parsed fields, inexpensive managed backups.
- Jobs: **Trigger.dev or Inngest** — scheduled rechecks, import parsing, alert evaluation, and retryable provider pulls with visibility; do not introduce Kafka/Redis in v1.
- File storage: **Cloudflare R2 or S3** — encrypted raw header/NDR/export originals; retain parsed/redacted extracts in Postgres and set lifecycle deletion.
- Auth: **Clerk or Supabase Auth with organizations/RBAC** — quick agency/client tenancy, MFA-capable access, and invitation flow.
- Observability: **Sentry + structured JSON logs + Postgres audit table** — trace parser/rule failures and preserve an explainable decision trail.
- Hosting: **Vercel + managed Postgres + worker platform** — low idle cost, preview deployments, and scale-up only after validated demand.
- MVP architecture: browser UI -> authenticated API -> Postgres evidence/case graph; uploads enter object storage -> async parser/normalizer -> rule evaluator -> hypothesis/runbook/packet generator; schedulers refresh evidence and notify owners. Provider adapters (Postmaster, SNDS, SES/ESP exports, seed tests) implement one normalized `EvidenceSource` contract and remain optional.

### Product Scope

- Incident intake for headers/NDRs, sender identity, flow, campaign, provider, volume, and business impact.
- Evidence board with authentication alignment, SMTP verdicts, provider/placement probes, reputation/blocklist checks, list health, forwarding path, confidence, freshness, and competing measurement-versus-placement hypotheses.
- Transparent ranked hypotheses with disconfirming evidence, required next evidence, and safety guardrails.
- Remediation checklist, controlled re-entry plan, owner/recheck schedule, and redacted provider-support packet.
- Portfolio view for domain/flow health and unresolved cases; no sending, warm-up automation, reputation score, or inbox guarantee in MVP.

### MVP Feature Set

- RFC header/NDR parser: SPF/DKIM/DMARC alignment, SMTP code, SCL/BCL, EHLO/PTR, provider, Return-Path, DKIM domain, sending IP, and forwarding hops.
- Case taxonomy: auth, reputation, blocklist, content, provider policy, list/volume, suppression, forwarding, and unknown.
- Deterministic rules: e.g., auth-pass plus provider Junk is not “resolved”; public blocklist-clean plus failed seed/recipient placement creates a provider-hidden-reputation hypothesis.
- Manual provider matrix for Gmail, Outlook.com, Yahoo, and corporate Microsoft 365, including `not observable`.
- Provider/flow metric comparison that records telemetry lag and every application using the sending domain; it must not label a Gmail-only open-rate change as placement without probe or recipient evidence.
- CSV/manual imports first; Postmaster/SNDS/SES/ESP connectors only after a paid-design-partner validates each adapter.

### Fast, Cheap, Maintainable, Scalable Rationale

- One TypeScript monolith and managed services minimize deployment, on-call, and synchronization cost.
- Async jobs isolate slow/fragile imports; a normalized evidence schema lets integrations be added without changing the case workflow.
- Postgres supports the MVP comfortably; scale jobs independently and partition evidence/audit tables before considering service decomposition.
- Rules are versioned data plus code tests, so recommendations remain explainable and reversible.

### Operational Tradeoffs

- Manual evidence makes the first release valuable but requires UX that rewards completeness; automated connectors are a paid expansion, not a launch dependency.
- Seed tests are directional rather than recipient truth; label them as probes and compare by provider/flow/time.
- Retain only redacted decisive fields by default; make raw artefact retention an explicit tenant policy.

### Open Questions

- Is the first paid buyer an agency/MSP, SaaS ops team, or ecommerce operator, and which has enough incident frequency to justify seats?
- Which first connector produces paid retention: Google Postmaster, Microsoft SNDS, SES, or a major ESP export?
- What evidence quality threshold should block automated remediation suggestions versus merely lower confidence?
